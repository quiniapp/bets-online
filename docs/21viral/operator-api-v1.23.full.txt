1.1 Terms used
In this document, we will refer to 21Viral as a Provider Game Server (PGS or simply Provider) and the
party which wants to integrate 21Viral games on their system as Operator Game Server (OGS or simply
Operator). Operator Game Server needs to be integrated with the 21Viral Provider Game Server in a
seamless way, so player funds always reside on the Operator Game Server. All player data, except
some basic information (playerId, currency and other relevant session related data found in start game
url request), reside on the Operator Game Server.

1.2 Purpose and overview
INTRODUCTION

This document outlines the integration protocol between Provider and the Operator, establishing a
comprehensive framework for game deployment and operation.

INTEGRATION COMPONENTS

   1. Game Launch Protocol - The initial phase requires Provider to facilitate player access by:
           Implementing mandatory security authentication
           Directing the Operator player's browser to a specifically formatted URL
   2. Operational Framework During active gameplay - The system maintains continuous
      communication through:
           Server-to-server requests from the Provider to Operator
           Secure data transmission protocols
           Real-time authentication verification

This dual-component structure ensures both secure game initialization and seamless operational
functionality while maintaining robust security standards throughout the gaming session.

All interaction between the provider and the operator will happen via JSON documents sent using
HTTP POST, over a secure HTTPS connection, using header Content-Type: application/
json; charset=utf-8 which is also required of the response.

Both parties (Provider and Operator) will always respond by returning a response JSON document, in
the format described by this document. Each incoming request from both parties will be verified using
the Hash Message Authentication Code (HMAC) with a SHA256 hash algorithm.

Shared secrets will be exchanged securely between the Provider and Operator.
Provider will provide an Operator, authentication username, and shared secret for each environment
where the provider is running, staging and production, along with IP addresses for whitelisting from
where the Provider will send requests to the Operator.

In the Provider's staging environment, requests to the Operator will originate from the following IP
addresses: 75.2.84.22 and 35.71.154.198

Operator will provide OPERATOR_BASE_API_URL for each environment, and the Provider will use it
in each request, as explained in further sections.

Every API request from Provider or from Operator, contains the following HTTP header:


   Authorization: HMAC-SHA256
   <authenticationUsername>:<hexEncodedHmacRequestSignature>



Each HMAC signature is built with request body complying to RFC 8785 ( JSON Canonicalization
Scheme ) based on which hex-encoded HMAC signature is generated.

2 Launching a game
All games supported by the Provider will be provided to the Operator via Provider API described below.
Those include all necessary game information to start game, such as game names, game categories,
game identifiers and default game thumbnails assets.

Beside basic game information which is available through Provider API, complete games configuration
can be provided as separate documentation.

As discussed previously, each request from Operator to Provider (same applies to Provider, needs to
include a well formed Authorization header ).



2.1 Tokens
The tokens are always created by the Provider. Provider is acting as an authentication server and it
keeps track of player sessions on behalf of the Operator. All requests during the game session,
besides the token, will contain additional information, such as the game being played and player's id.
All tokens will expire after a period of unused time within the game session. Player in-game actions
will always reset the token expiration timer. Provider generates random and unpredictable tokens.
Tokens will be generated by Provider with the same rigorous level of randomness and security that
one would use for encryption keys.



2.2 OperatorGamesRequest (from Operator to Provider)
Provider returns a list of the all available games to the Operator system. The list contains game details
needed to launch a game via OperatorStartGameUrlRequest.



         In production, the request is limited to one call per hour to maintain the Provider’s platform
         performance.




         We recommend fetching the games regularly, for example once a day.
         This way, you’ll always be in sync with updates such as:
              new game releases;
              new game providers added;
              disabled or removed games;
              renamed games, etc.

         The list of games returned via the API is sorted by game ID, making it easy to compare it with your
         own list, either automatically or manually.

3.2 Game round/bet types
The Provider game system considers that there are four possible types of game rounds:

   1. Cash round. The bet is paid with cash money.

   2. Promo round. The bet is paid with promo money, provided by the Operator, for example first
      deposit bonus. Possible only if Operator supports promo wallets.
   3. OperatorFreeSpinBonus round. Bet is paid with a free credit provided and tracked by the
      Operator, for example as part of a marketing campaign, or as a deposit bonus mechanism.
      Possible if Operator supports this and if target games support this. Defined with freeSpins
      and freeStake response fields in ProviderGetBalanceRequest and
      ProviderGameTransactionRequest .

   4. ProviderFreeSpinBonus round. The bet is paid with a free credit provided
      and tracked by the Provider, for example as part of a free spins marketing campaign.

3.4 Idempotence
When sending API requests, if anything goes wrong, or simply getting the response takes too long,
Provider will re-send the same request. Therefore the Operator must expect to receive the same
request multiple times. In such case, the operation requested must only be performed once. Upon
requesting the same operation twice, the second request should be responded to identically as the
first response, but the operation should not modify anything.



                                                                                                Provider API – 18
                                                                                Development – Operator API




Idempotence should not be applied at all to ProviderGetBalanceRequest. Each such request should be
processed as a new request.

Example:

   1. Game starts, Provider sends ProviderGetBalanceRequest

   2. Operator responds with player balance "100.00"

   3. Provider sends ProviderTransactionRequest of type "Debit" with amount "1.00"
      and providerTransactionId being "10001:43827022-9b1e-42b2-
      a2d8-3288ec02f6e9"

   4. Operator deducts the player's account, and responds with success and balance "99.00"
   5. The above response is lost due to any kind of network error
   6. Provider will again request ProviderTransactionRequest of type "Debit" with amount
      "1.00" and providerTransactionId being "10001:43827022-9b1e-42b2-
      a2d8-3288ec02f6e9"

   7. Operator notes that bet reference "10001:43827022-9b1e-42b2-a2d8-3288ec02f6e9"
      of type "Debit" has already been successfully processed, and has not been canceled, and the
      requesting user and amount are identical to the earlier request, therefore the Operator does not
      deduct the bet second time, and responds with success and balance being "99.00" and with
      alreadyProcessed being true .

   8. Operator should not rely providerTransactionId being only information based on which
      idempotency should be performed. In some case providerTransactionId will be the same
      for "Debit" , "Credit" and "Reversal" , best to check against
      providerTransactionId and transactionType , other relevant player information like
      game being played and unique playerId.

3.6 Error handling
If the Operator encounters an error while processing a request from the Provider API, it must return an
error with appropriate HTTP status code and with appropriate response body as follows:


  {
      "viralErrorCode": "{VIRAL_ERROR_CODE}",
      "message": "{ERROR_MESSAGE}"
  }



{ERROR_MESSAGE} is an human readable string to assist in debugging and troubleshooting.

5.4 Authentication and Security
Both jackpot API endpoints follow the same HMAC-SHA256 authentication mechanism as other
Provider APIs:


   Authorization: HMAC-SHA256 <authenticationUsername>:<hexEncodedHmacRequestSignature>



The HMAC signature is generated using the request body in canonical JSON format (RFC 8785) and
the shared secret.



5.5 Error Handling
If the Provider encounters an error while processing a jackpot request, it returns an error response with
appropriate HTTP status code and the standard error format:


   {
       "success": false,
       "errorMessage": "{ERROR_MESSAGE}",
       "timestamp": 1694592000000,
       "providerName": "pragmatic",
       "count": 0
   }



Common error scenarios:

       Provider Not Supported: When requesting jackpots from a provider that doesn't support jackpot
       APIs
       Invalid Time Range: When startTime is greater than endTime in winners request
       Authentication Failure: When HMAC signature validation fails
       Provider API Unavailable: When the underlying provider's jackpot API is temporarily unavailable



5.6 Implementation Notes
   1. Provider Support: Currently, only Pragmatic Play provider supports jackpot APIs. Other providers
      will return empty results or appropriate error messages.

2. Fallback Behavior: If the underlying provider API is unavailable, the system may return mock
   data or cached results to ensure service availability.
3. Rate Limiting: Consider implementing appropriate rate limiting for jackpot API calls to avoid
   overwhelming provider systems.
4. Data Freshness: Jackpot amounts are updated in real-time from provider systems. However,
   there may be slight delays due to network latency and caching.
5. Currency Filtering: When currency parameter is provided, only jackpots/winners matching that
   currency are returned. If omitted, results for all supported currencies are included.

HMAC validation fails

      Solution: Ensure JSON keys are sorted alphabetically before generating HMAC

      Solution: Use future timestamps for duration.expiration

8 Usage of "/games" API method
 1. Operator's technical team should read and follow the "Operator API" manual to integrate 21Viral
    service into their iGaming platform.
 2. One of the API methods to be integrated is "/v1/games" API method, which is described in the
    "OperatorGamesRequest" section of the document.
    This method shall be used to fetch the list of 21Viral games via API (automatically).


    We recommend fetching the games regularly, for example once a day.
    This way, they will always be in sync with the game updates such as:
         new game releases;
         new game providers added;
         disabled or removed games;
         renamed games, etc.


    For information, the list of games returned via the API is sorted by "id" parameter. "id" stands for
    identifier.
 3. When Operator's platform fetches the games for 1st time, the list of game just needs to be
    stored in Operator's Database.
 4. When Operator's platform fetches the games again, it should compare the new list (from "/v1/
    games" API method) with the existing one in the Operator's Database. The comparison shall be
    done by "id" parameter of the games.
    Possible cases:
         if a game is found in the new list, then it shall be added to the Operator's Database;
         if a game from Operator's Database is not found in the new list, then it shall be disabled or
         removed in the Operator's Database;
         if one of the game parameters (name, type, defaultLogo, providerName, providerGameId,
         rtp or hasFreeSpins) is changed, then it shall be changed in the Operator's Database as
         well.
